## 2026-11-20, confine machine pages to their mount (#742)

- A machine's answers hold paths (`newUntitled`'s `path`, for one) that Jupyter's Drive joins onto the base URL. A path like `../../../api/contents/...` resolved to this device's own server, which the app token authenticates. A machine is less trusted than this device.
- For a config with `machine` set, `settingsFor` (used by `connectTo`) now gives `ServerConnection.makeSettings` a `fetch` and a `WebSocket` that refuse, before any network call, a URL that doesn't resolve to the page's origin under `/machines/<id>/`.
- Found while testing: `@jupyterlab/services` already refuses the issue's example. `URLExt.join` resolves the `..` itself and `handleRequest` throws for a URL that no longer starts with `baseUrl`. So the guard is the transport-level backstop for any request that reaches `fetch` or `WebSocket` some other way (an absolute URL, a later version of the library), not the only check.
- `isUnderMount` judges the resolved URL (`new URL` drops `.`, `..` and `%2e` segments as the browser does), so it checks where a request lands, not how it is spelled. The prefix ends in a slash, so `/machines/<id>x/` is refused too.
- The 'page' and 'both' kernel variants reuse the same settings. `createMixedServices` rebuilt them with `dispatchingSocket`, which dialed server sockets with the global `WebSocket` and would have dropped the guard in 'both' mode. It now takes the incoming `serverSettings.WebSocket` for server sockets. Other configs are unchanged.
- Tests: `src/lib/backends-confine.test.ts` for the pieces; `src/lib/backends.test.ts` for the wiring, on the settings a real `connect()` of a machine config returns (a climbing request never reaches `fetch`, a climbing socket throws, and a `NotebookRoom` join with a climbing `fileId` opens no socket); `src/lib/mixed.test.ts` for server sockets going through the given `WebSocket`. Each fails when its line is removed from `settingsFor`, `connectTo` or `dispatchingSocket`.
