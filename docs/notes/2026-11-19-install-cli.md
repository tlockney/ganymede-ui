## 2026-11-19, Install the command line tool from the Mac app (#686)

The Mac app bundles the `ganymede` binary in `Contents/Helpers` and Settings › General › Command Line Tool (and an app-menu item that opens it) links it to `~/.local/bin/ganymede`. `CommandLineTool.swift` holds the logic with the bundle, link, PATH and file manager passed in; `CommandLineToolTests` runs it in temporary folders.

Notes:

- Install creates a symbolic link and nothing else: no copy, no admin prompt. A link is ours when its target ends in `.app/Contents/Helpers/ganymede`, so a stale link from a moved or replaced app is replaced (Update Link) and removed by Uninstall. Anything else at the path (a file, a folder, a link elsewhere, `install.sh`'s binary, Homebrew's link) is never touched: install and uninstall refuse and the message says what is there and how to move it. Settings offers Replace… for that case: a confirmation, then `FileManager.trashItem` on the file or link itself (so a link's target is never touched; `install(force:)` takes the trash function so tests don't fill the real Trash), then the install. If the Trash fails the item stays and the error says so. Settings always shows the link path, `~/.local/bin/ganymede`. The new link is made beside the old and renamed over it, so a failure leaves the old one.
- A link to an app run from Gatekeeper's `AppTranslocation` copy would break at the next launch, so install refuses until the app is moved to Applications.
- Settings shows the `~/.zprofile` line when `~/.local/bin` isn't on the PATH the app adopted from the login shell (`LoginShell`), and names another `ganymede` on it (`AppMCP.ganymedeCommand`, with its `--version` run off the main thread, 3 s limit) in every state but "not in this build", unless it is our link or leads to the bundled tool. The PATH text says the app's PATH comes from `$SHELL -l`, so a line in `~/.zshrc` reaches terminals but not the app or Claude Desktop; it names `~/.zprofile` only for zsh. Claude Desktop's MCP config uses the bundled tool's path when no `ganymede` is on that PATH (`desktopCommand`).
- `bootstrap.sh` bundles a CLI from `GANYMEDE_CLI`, a `GANYMEDE_DIR` build, or a `GANYMEDE_REF` release later than v0.13.0, and otherwise skips it with a message: `ganymede update` up to 0.13.0 overwrites the binary where it runs and would break the app's signature (ganymede#883). CI pins v0.13.0, so its app has no tool and the section is hidden; the code path with a tool is covered by the unit tests only until the pin moves. The release tarball unpacks to `ganymede-<version>-aarch64-apple-darwin/ganymede`, as `install.sh` does.
- The build phase copies and signs the tool (ad hoc or the build's identity, hardened runtime), and removes a copy an earlier build left when there is none now. `build/cli` may not exist, so it can't be a declared input: script sandboxing is off for the `Ganymede` target. `release-app.sh` signs the helper with the release identity and timestamp before the app; `check-app-bundle.sh` runs `--version` on it when present.
- Not done: a prompt at launch, `/usr/local/bin`, an Intel build, or checking the tool's version against the app's.
