## 2026-11-04, drag and drop (#216)

- Each cell has a drag handle (six dots) under its "…" button, with the
  other touch controls of #200: on touch screens and in narrow windows.
  JupyterLab's own drag, from a cell's prompt, is mouse-only, so on an
  iPhone or an iPad without a trackpad cells could only move one step at
  a time from the cell menu.
- The handle uses pointer events, so a finger, a pencil and a mouse all
  work, and captures the pointer, so a drag that leaves the handle keeps
  coming to it. `touch-action: none` on the handle keeps a finger on it
  from scrolling the notebook. Past 4px the press is a drag: the cell
  follows the pointer, a line shows where it lands (after every other
  cell whose middle is above the pointer), and the notebook scrolls near
  its top and bottom edges. Escape, a cancelled pointer, or any change to
  the cells meanwhile (an undo, another window) leaves it where it was.
- The move is `NotebookActions.moveCells`, as JupyterLab's drop uses: one
  change to the notebook model, so it marks the notebook dirty, is saved,
  and is undone and redone with Z and Shift+Z, and a running cell keeps
  its output. The handle is plain DOM added by `cell-controls.ts`, whose
  capture-phase `pointerdown` listener (which keeps taps on controls from
  the notebook) starts the drag in `src/lib/cell-drag.ts`.
- Notebooks dropped from Finder or Files arrive as an HTML5 drop with
  `File` objects. `src/lib/file-drop.ts` reads each one, checks it is a
  notebook (JSON with an `nbformat`), and saves it into the folder through
  the contents API, so it works on a server and in the browser's storage
  alike. On the sidebar that is the folder it shows; on the notebook
  window it is the same folder, and the first notebook dropped opens.
- A taken name gets `-Copy1`, `-Copy2`, … as Jupyter names a duplicate
  (#203), compared without case since a Mac's disk doesn't tell `io` from
  `Io`. The folder is listed once per drop, so two notebooks of the same
  name dropped together both get a free one.
- The drop handlers are on the capture phase, so a notebook dropped on a
  cell's editor isn't pasted into it as text by CodeMirror. Other files
  are left to what is under the pointer (an editor still takes a text
  file); a file nothing takes is refused with a message instead of the
  web view showing it in place of the app.
- The handle is pointer only: it is out of the tab order and hidden from
  VoiceOver, since the … menu's Move Up and Move Down already serve the
  keyboard. Errors from a drop of several files show one per line.
- Unit tests drive the handle with pointer events on a real notebook in
  jsdom (cells laid out 100px tall) and the drop with jsdom's drag events.
  The drop as WKWebView delivers it from Finder and Files, and the drag
  under a finger, are checked by hand on a device.
