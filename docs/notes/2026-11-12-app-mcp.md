## 2026-11-12, MCP from the Mac app (#304)

Settings › General › MCP turns on `/mcp` on the app's in-process server:
Off (default), Read only, Edit don't run, Edit and run, and whether
images go to the model. These are ganymede.toml's `mcp_enabled`,
`mcp_read_only`, `mcp_no_execute` and `mcp_images`, passed through the
FFI's config as before; no FFI change.

Discovery: agents are configured with `ganymede mcp` (Thomas's call,
2026-11-12), the same config whether the app runs or not. While MCP is
on the app writes `jpserver-<pid>.json` itself (Swift, mode 0600, removed
when the server stops), so `ganymede mcp` finds the app's server, rooted
at `/`, and forwards to it; without the app it runs its own. Written by
the app rather than the embedded server so the app stays on a released
ganymede. `find_server` prefers the deepest root, so a project's own
`ganymede serve` still wins over the app. The app's root being `/` made
an agent's relative paths start at `/`: ganymede#730 (issue #729) has
`ganymede mcp` send the agent's folder on `initialize`, and the server
resolves relative paths from it.

For clients without the CLI, Settings also shows
`claude mcp add --transport http` with the token in an `Authorization`
header. For that config to outlast a restart, the server's token is,
while MCP is on, one the app keeps in the keychain (`mcp.token`); the
port was already kept across launches.

`ganymede mcp` picks its server once, at start: an agent started before
the app keeps its own server, and the app shows the notebooks it holds
read-only (room locks, #272). Switching mid-session would drop the
agent's kernel state.

A fixed-port setting was not added: the kept port makes it mostly
unneeded.

A change restarts the server, as moving kernels to a remote does, so
turning MCP off ends agents' sessions; kernels restart with it. Toggling
`/mcp` on a running server would need a ganymede API.

Network surface: loopback only (the app's server binds 127.0.0.1), token
required; `/mcp` isn't routed while off.
