## 2026-11-19, DuckDB console (#679)

A DuckDB prompt in the page: `DuckdbConsole` (`src/components/DuckdbConsole.tsx`) is the view, `src/lib/duckdb-console.ts` the logic, on `openEngine` from `parquet.ts`.

Design:

- **No path, a folder.** The console is `App` state (`duckFolder`), not a pseudo-path, so `?open=`, `titleFor`, recents, `postDocument` and the file actions never see a fake file. It shows where a notebook would, when no `openPath` is set; `new-duckdb-console` sets `openPath` to undefined (the notebook unmounts and autosaves, as when another opens) and sets the folder; setting any `openPath` clears it, and the app's `close` command closes it. The app's state posts `path: null`, so `PageState.hasNotebook` is false and every notebook menu, the toolbar and the subtitle disable with no Swift state change. The palette entry, `new-duckdb-console` in `PAGE_COMMANDS`, File > New DuckDB Console on the Mac (`NewCommands`, folder as argument) and on the iPad (`IPadNewNotebook`, argument empty: the notebook folder, as New Notebook).
- **Input** is a CodeMirror `EditorView` with `@codemirror/view` and `@codemirror/state` only; no `@codemirror/commands` (not a direct dependency), so Enter, Shift-Enter, ↑ and ↓ are our keymap, and there is no undo history. Enter runs when `endsStatement` says the input ends with a `;` (or is a dot command), else inserts a newline.
- **SQL reading** (`pieces`) is a small lexer: code, `'strings'` (`''` escapes), `"names"`, `$tag$` strings, `--` comments and nested block comments. `statementsOf`, `endsStatement` and `filePaths` use it, so a `;` or a path inside a string or comment means nothing. An unterminated string or comment makes Enter add a line.
- **Files.** A single-quoted literal ending in `.csv`, `.tsv`, `.json` or `.parquet` is read through `readBytes` with `whole = true` and the data view's limits (8, 16 and 64 MB; `limitFor`) and registered in DuckDB under the text as written, so the statement runs unchanged. Whole, not cut: a query over half a CSV answers wrongly, so the view's 8 MB truncation isn't used. Paths resolve against the window's folder and a `..` past it is refused; URLs, absolute paths and wildcards go to DuckDB. A file the server says is missing (404) isn't an error of ours: the statement runs and DuckDB's "No files found" shows (a `copy ... to 'out.csv'` names a file that isn't there yet). Too large and other read errors stop the statement before it runs. A file is read once per console (the registered names are kept), so a change on disk shows in a new console.
- **Results** come from the Arrow table the statement returns, typed by Arrow's field types (`cellOf`): decimals through their scale, dates and timestamps as `YYYY-MM-DD[ HH:MM:SS]`, times, and lists, structs and maps as JSON text; 64-bit integers past 2^53 stay text. Intervals show as raw JSON for now. A result with no columns, or DuckDB's `Count` column for `create`, `insert`, `update`, `delete`, `copy` and `merge`, becomes `OK` or `N rows affected`. A table is capped at 10,000 rows with the count kept.
- **Session.** `ConsoleSession` runs statements through a promise chain, so two Enters never interleave on the connection, and keeps `ran` (the statements that succeeded, dot commands left out) and `files`. `close` is once. The component starts the engine in an effect and closes it in the cleanup, also when the effect is cleaned up before the engine started. There is no cancel of a running statement.
- **Export.** `consoleNotebook` makes a title cell, a `jupyter.sql.load("<table>_file", "<path>")` cell for each file read and a `jupyter.sql` template cell for each statement that ran (`templateText` escapes `\`, backtick and `${`, so the kernel reads the text back as typed). The load tables get `_file` after the name so a `create table moons as select * from 'moons.csv'` later in the notebook doesn't meet a table of the same name. The paths are relative to the notebook, which is saved in the folder. `freePath` picks `duckdb-console 2.ipynb` when the name is taken. The statements still read files by path, so the load cells show what the notebook needs more than they supply it.

Tests: `duckdb-console.test.ts` (reading SQL, the Enter rule, history, file paths, session against a stand-in engine, export cells), `duckdb-console.real.test.ts` (the real duckdb-wasm Node build: CSV, TSV, JSON and Parquet by relative path, tables kept, result types), `DuckdbConsole.test.tsx` (the component with a stand-in engine: keys, errors, history, files, engine close, export), `App.test.tsx` and `palette.test.ts`, and `e2e/duckdb-console.spec.ts` against the real wasm (served from `node_modules` in place of jsDelivr, as `offline-sql.spec.ts` does), including that the worker is gone after the console closes. The Node build can't throw DuckDB errors (`_setThrew is not defined`), so errors are tested with the stand-in and in e2e. `e2e/data/moons.parquet` is a 481-byte file written with DuckDB; it is outside `e2e/fixtures` so it isn't seeded into every test's folder.

Not done: a cancel for a long statement, re-reading a file that changed, writing files to the folder, syntax highlighting and completion (no SQL language package), `.help`, a result in the scrollback that survives closing the console.

By hand (for #399 and #273), Mac and iPad, a build of `main`:

1. File > New DuckDB Console (Mac), File > New DuckDB Console (iPad), and the Command Palette entry each open the console in the window. With a notebook open, it closes in favour of the console (edits saved); the notebook menus (Run All, Kernel, Save…), toolbar buttons and the window subtitle are disabled or empty while it shows. Opening a notebook from the sidebar, or the window's close, leaves it.
2. First run online: "Starting DuckDB…" then the prompt. `select 42 as answer;` + Enter shows a one-row table. Offline (after one run), a new console still starts.
3. `select 1` + Enter adds a line, Shift-Enter runs; `select 1; select 2;` shows two results; `select 'a;b';` runs once. ↑ and ↓ bring back earlier statements; in a multi-line input they move the cursor.
4. In a folder with a CSV, a TSV, a JSON and a Parquet file: `select * from 'name.csv';` and the others show their rows (a subfolder as `'sub/name.parquet'`). A missing file shows DuckDB's error; `'../x.csv'` shows "outside this window's folder"; a file over the limit (CSV 8 MB) says so.
5. `create table t as select * from 'name.csv';` then `select count(*) from t;` works; a typo shows the error and the next statement still runs; `.tables` and `.schema t` work.
6. Export to Notebook is disabled until a statement succeeds, then writes `duckdb-console.ipynb` in the folder (a second export writes `duckdb-console 2.ipynb`) and opens it; run it on a TypeScript kernel on a server (cdp-node) and the cells give the same results. On the iPad, the in-app kernel can't find the files by name.
7. Close the console (open a notebook): Activity Monitor or the Web Inspector's Workers shows the DuckDB worker gone. Open and close it a few times on the iPhone and iPad for memory.
8. Dark mode and a narrow window: the input, scrollback and a wide table scroll without moving the page.
