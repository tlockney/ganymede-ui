## 2026-11-14, the app's MCP token opens only /mcp (#583)

The Mac app passed its keychain MCP token as the server's `token`, so the
token Settings shows for HTTP agents opened every REST and websocket
route, whatever the MCP mode: a Read only agent could still write files,
start kernels and change grants over REST. ganymede#781 (#766) added
`mcp_token`, which `/mcp` accepts and no other route does.

`AppMCP.serverConfig` now passes the keychain token as `mcp_token` and
leaves `token` unset, so the server makes its own random token per launch,
which the page gets through the server's URL. Off and Reset Token revoke
the keychain token as before.

The server info file that `ganymede mcp` reads holds `mcp_token` too, not
the server's token as `ganymede serve` writes it. `ganymede mcp` keeps the
token it found for the whole session (on a 404 it re-initializes with the
same URL and token; only `ganymede mcp watch` looks for the server again),
so a per-launch token there broke a running agent session with 403s after
any mode change or relaunch; the keychain token survives restarts. It
also keeps the server's own token off disk. `ganymede mcp` (proxy, `call`,
`watch`) sends its token only to `/mcp`, so nothing it does needs more.

That confines an agent only while it can't run code: a cell can read the
server's own token, and an agent reads any output that shows it.
`GANYMEDE_REF` moves to ganymede's main at #781, so the XCFramework is
built from source until the next ganymede release; an older one refuses
`mcp_token` (`Config` denies unknown fields).

Review follow-ups: `docs/apps.md` says other readers of the app's server
info file, such as `jupyter server list`, get a URL the server refuses,
and that Reset Token needs running `ganymede mcp` agents restarted (the
proxy never re-reads the file). Ganymede's reference page says the same
in its ganymede-ui note.
