## Facts

- Server side is merged in ganymede (#973): the app's mount
  `/machines/{id}/` now forwards `api/host/grants/{path}` (GET, PUT,
  DELETE). The app bundles ganymede at `GANYMEDE_REF`, which is still
  the last release, so until that bump the mount answers 404 for it.
  The UI must handle that 404 gracefully (see below).
- Web: `src/lib/host-grants.ts` `hostGrantsAvailable(backend)` returns
  false for `backend.config.machine` with a comment citing #701.
  `answer()` already maps a bare 404 to "This server has no notebook
  access settings. They need a newer Ganymede." `src/App.tsx` uses
  `hostGrantsAvailable` for the `notebook-access` command (~849), the
  "wants" padlock check (~961) and the `hostGrants` flag sent to native
  chrome (~1040, ~1364).
- Native: `Place.opensExternally(_:)` (apple/Sources/Ganymede/Place.swift)
  lets only http(s) out of a machine's window; `WebView.swift`
  `decidePolicyFor` (~412) and `createWebViewWith` (~540) call it.
  `AppURL(url)` (AppURL.swift) parses `ganymede://` links into
  `Command` (`.open(path:)`, `.openInFolder`, `.new`, `.run`) plus an
  optional x-callback. A window opens a notebook by path with
  `page.run("open", arg: path)` (see IPadChrome.swift); `WebView`'s
  coordinator has `page: PageModel?`.

## Changes

1. Web, Notebook Access:
   - `hostGrantsAvailable`: true for a machine backend too (still false
     for `kernels === 'page'` and non-Ganymede). Update the comment.
   - The padlock "wants" check must not show an error when the grant
     GET fails with 404 (an app whose bundled server predates #973):
     treat it as "no grant info" and show nothing. Opening Notebook
     Access itself shows the existing 404 message.
   - Tests in the existing host-grants / App tests: a machine backend is
     available; the wants check stays quiet on 404.
2. Native, app links in a machine's window:
   - Add a pure function in Place.swift, e.g.
     `func machineLink(_ url: URL) -> MachineLink` where
     `enum MachineLink: Equatable { case notApp; case open(path: String); case refused }`:
     - not `ganymede://` → `.notApp` (web links keep today's path);
     - this device → never called (keep today's behaviour: `appLinks`
       allowed, `opensExternally` true);
     - a machine: `ganymede://open?path=P` with P relative (no leading
       `/`, no `~`, no empty / `.` / `..` segment, no x-callback) →
       `.open(path: P)`; everything else (`run`, `new`,
       `open?folder=&file=`, x-callback-url, absolute, `~`, `..`,
       unparseable) → `.refused`.
   - WebView: in a machine's window, a `ganymede://` link (both the
     link-activated path and `createWebViewWith`) goes through it:
     `.open(path)` → `page?.run("open", arg: path)`; `.refused` →
     show "This link names a file on another computer." the way the
     window shows other short notices (find an existing alert/notice in
     WebView or the chrome; on iOS the same). Never call
     `openExternally` / `AppURLHandler` for a machine's `ganymede://`
     link. `appLinks` in `Place.allows` stays this-device only.
   - PlaceTests: one test per case above.
3. docs/apps.md, Machines section: Notebook Access works in a machine's
   window and edits that machine's settings (needs an app whose bundled
   server includes ganymede#973); `ganymede://open` links in a
   machine's notebook open that machine's file in the same window,
   other app links are refused there. Under an `**Unreleased.**` note
   (extend the section's note or add one next to the new text).
4. Dev log docs/notes/2026-11-26-machine-access-links.md, starting
   `## 2026-11-26, Notebook Access and app links on a machine (#868)`.
5. By-hand checks as comments on #399 (Mac) and #273 (iPad/iPhone),
   ending with `---\n_Generated by [Claude Code](https://claude.ai/code)_`:
   Notebook Access in a machine's window (with a new-enough bundled
   server: reads and saves the machine's grant; with the current one:
   the "newer Ganymede" message, no padlock error); a
   `ganymede://open?path=` link in a machine's notebook opens that
